# 決策紀錄

新決策往下加,不要改寫舊的(要推翻就新增一條寫「取代 #N」)。

## 已定案

### 1. 資料庫用 Neon,不用 Firebase
Cloudflare Workers 沒有原生 TCP socket,Neon 有 HTTP driver(`@neondatabase/serverless`)可直接在
Worker 裡用。Firestore 的 NoSQL 模型也做不到這個專案需要的「關聯查詢 + 向量相似度」。

### 2. 後端用 Cloudflare Workers + Hono
沿用使用者既有的 Cloudflare 部署經驗;與前端 Pages 分開部署,未來行動端可共用同一套 API。

### 3. 前端用 React(Vite SPA),不用 Svelte/Next.js
理由是對 AI coding 工具最友善、可參考知名開源專案的互動模式、為未來行動 App 鋪路。
不用 Next.js 是因為這個專案不需要 SSR,SPA + Pages 部署最單純。

### 4. 圖視覺化用 Sigma.js + graphology,不用 Cytoscape
舊專案用 Cytoscape,文件太少、開發體驗差。Sigma.js 定位是「嚴謹的網絡分析工具」,與本專案的
社群偵測/中心性分析深度相符,WebGL 渲染也撐得住大圖。

### 5. Monorepo 用 npm workspaces
不用 pnpm(使用者明確不想踩奇怪的 bug),不用 yarn。

### 6. 排程拆成兩種
- 輕量每日(抓最新瀏覽量、更新彙總、跑異常偵測)→ Cloudflare Cron Trigger,純 API + 算術,吃得下。
- 重量週期(重爬 + 社群偵測 + embedding)→ GitHub Actions。Workers 是 V8 isolate,沒有 Python
  runtime,igraph/Infomap 根本跑不動,CPU 時間也不夠。

### 7. Embedding 模型暫定 `@cf/baai/bge-m3`(1024 維)
Workers AI 上的多語系模型,涵蓋中文;維度剛好與舊 schema 的 `vector(1024)` 一致。
**離線 pipeline 與線上 Worker 必須用同一個模型**,否則向量空間不相容。
定義在 `packages/db-schema/src/config.ts` 與 `pipeline/wiki_pipeline/config.py`,兩處要一致。
→ 仍待使用者最終確認(見「待決事項」)。

### 8. Schema 相對舊版的取捨
- 表名去掉繪圖庫綁定:`topology_relation_cytoscape_nodes/edges` → `topology_view_nodes/edges`;
  `topology_relation_graph_*` → `topology_*`;`topology_subgraph_*` → `community_subgraph_*`。
- **捨棄** `nodes_query_vector`:查詢 embedding 由 Worker 即時呼叫 Workers AI 產生,不需預存。
- **捨棄** `vector_relation_graph_nodes/edges`、`vector_graph_edges`、
  `subgraph_edges_cosine_similarity`、無型別的舊 `subgraph_edges`:v1 功能清單裡沒有
  「向量相似度圖」這個視圖,先不做。日後要加再開新表。
- **新增** `community_special_nodes`:舊 schema 沒地方存 hub/authority/betweenness/bridge 標記,
  但社群子圖 UI 需要。
- 所有 `bigint` 改成 `integer`:節點數不可能超過 21 億,`bigint` 在 JS 端只會製造麻煩。
- 全面補上主鍵與外鍵(舊版很多表連主鍵都沒有,會產生重複資料)。

### 9. 開發用小型 fixture 種子
`DEV_SEEDS = ["圖論", "網絡科學", "複雜網絡"]`(三個都實測存在;原本寫的「社群發現」zh 維基沒有這個條目)、depth 2。這不是最終作品集主題,只是讓
Phase 1-6 有東西可開發,不被主題決策卡住。社群過濾門檻在 dev 設定裡調成 min=3/max=200
(舊版寫死 50/500,小圖會濾光所有社群)。

### 10. 標題以維基的「正式標題」為圖的 ID
zh 維基的正式頁面標題簡繁混雜(「圖論」的實際頁面是「图论」、「網絡科學」是「网络科学」)。
所有 API 呼叫都帶 `converttitles=1` + `variant=zh-tw`,並在展開前用 `WikiClient.resolve_titles`
把佇列裡的標題收斂成正式標題,否則同一個條目會變成兩個節點、圖也會斷開。
`displaytitle` 實測**不會**做繁簡轉換,所以「顯示用繁體標題」要另外想辦法(見待決事項 G)。

### 11. Phase 1 爬蟲改成逐層 BFS
舊版是遞迴 DFS + 序列化請求。新版一層一層跑,每批(預設 concurrency×4)先批次收斂標題、
再併發抓連結、最後整批寫進一個 SQLite 交易。好處:進度可續傳、中斷不會留半筆、
同一批裡指向同一頁的別名只抓一次。

### 12. 顯示標題用 OpenCC(s2twp)在 pipeline 端轉換
`nodes.title` 存維基正式標題(圖的 ID、組維基連結用),`nodes.title_display` 存 OpenCC
`s2twp` 轉出的台灣繁體,前端顯示一律用後者。實測:「计算机科学」→「電腦科學」、
「人工智能」→「人工智慧」、「数据结构」→「資料結構」,與 MediaWiki `variant=zh-tw`
回傳的簡介內文用詞一致(都用「網路/演算法/軟體」),標題與內文才不會打架。

選 pipeline 端而不是前端轉換:前端要多載一份字典、上千個節點每次渲染都要轉;
pipeline 只在爬取時轉一次,而且搜尋時兩種寫法都能比對。

### 13. Phase 2 用 igraph 內建的 `community_infomap`,不裝 infomap 套件
舊版 `analyze.py` import 了 `infomap`,但實際跑的是 `G.community_infomap()`(igraph 內建)。
新版照做,少一個原生依賴,GitHub Actions 的重算 workflow 也少一個編譯風險。

### 14. meta-graph 不建「沒有連結」的社群配對邊
舊版對所有社群兩兩建邊,沒有跨社群連結的邊 `connections_num=0`、`distance=inf`。
這種邊會讓加權 pagerank(權重 0)與加權 betweenness(權重 inf)失去意義,
而且對前端只是雜訊。新版只建 `connections_num > 0` 的邊;center 之間在有向圖上走不到時,
distance 給「最遠有限距離 + 1」而不是 inf。資訊等價,數值可用。

### 15. 主畫面的「拓樸圖」= 社群關係 meta-graph
沿用舊版的資訊架構:主畫面不是整張連結圖(太大),而是每個有效社群 4 個特殊節點
(hub / authority / center / bridge)構成的關係圖,點進社群才看該社群的子圖。
⚠️ 這件事與 `packages/db-schema` 目前的 `topology_nodes` 註解(寫成「全圖節點」)不一致,
Phase 4 要一起處理,見待決事項 H。

### 16. 社群偵測固定亂數種子
Infomap 是隨機演算法:同一張圖連跑兩次,實測給出 35 / 36 / 39 個社群,membership 也不同。
社群編號會寫進資料庫、也會出現在前端網址裡,每週重算就換一次號碼是不能接受的。
`detect_communities()` 預設用 `DEFAULT_SEED = 20260818`(實測固定種子兩次跑出完全相同的
membership);要評估分群穩不穩定時傳 `seed=None`。

### 17. meta-graph 一個條目只有一個頂點
同一個條目常常同時是 hub 與 center(社群裡最大的節點通吃),舊版是每個角色各建一個頂點,
前端就會畫出重複節點。新版一個 idx 只建一個頂點,角色合併成 `roles`(逗號分隔)。

### 18. 瀏覽量只抓每日,半月/平均/社群加總都在本地算
舊版只抓 monthly,拿不到日資料就做不了每日異常偵測。新版一律抓 daily,半月(每月 1-15 標成
01、16-月底標成 16)、平均、社群加總都用 `pageviews.py` 在本地算:少打一輪 API,而且兩種
粒度的數字保證對得起來。

⚠️ 資料量:13,085 個條目 × 365 天 ≈ 478 萬筆。本機 SQLite 沒問題,但 Neon 免費方案只有
0.5 GB,估計光這張表加索引就要 300 MB 以上。Phase 4 要決定怎麼處理(見待決事項 I)。

### 19. 抓簡介的批次大小是 20,不是 50
MediaWiki TextExtracts 每個請求最多回 20 筆 extract,超過的部分靜默省略(不報錯、沒有
warnings)。實測用 50 個標題一批,13,085 個條目只有 5,240 個拿到簡介 —— 剛好 40% = 20/50。
`fetch_extracts` 現在超過 20 個標題會直接丟 ValueError,寧可當場爆掉也不要靜默漏資料。

### 20. 瀏覽量抓取併發上限 6,且開發階段不抓滿
實測 Wikimedia REST pageviews API:併發 6 抓 100 個條目 0 失敗;併發 12 持續抓大量條目時
會被限流,約 10% 的條目重試 4 次後仍失敗(續跑會自動重抓)。`PageviewsConfig.concurrency`
預設 6,並在 429/503 時尊重 `Retry-After` 標頭。

瀏覽量不是這個作品集的核心賣點(核心是連結網絡 + 社群偵測 + 語意搜尋),所以開發階段
只抓到約 5,700 個條目(160 萬筆日資料)就停,不花 45 分鐘抓滿 —— 這些真實資料足夠開發
Phase 4-6,而且比寫一份之後要丟掉的 mock 產生器省事。全量抓取留到 Phase 8。

### 21. 探索性實驗的數字要進版控(腳本,不只是結論)
2026-08-19 的討論靠幾個一次性腳本量出了會改變架構的數字(封閉度 2.4%、跨群邊 7%、
瀏覽量集中度、conductance 排序)。這些腳本收進 `pipeline/experiments/`,理由是
**一個沒辦法被重跑的數字,不能拿來做架構決策**。

它們刻意不進 CI、不寫測試、不寫入任何東西 —— 是探索工具,不是 pipeline 的一部分。
維基百科本身會變,所以重跑的數字不會與文件完全一致;但結論(排序、量級、方向)
應該還成立,如果連結論都翻了就是真的發現,要回去改文件。

### 22. 資料策略的討論記錄與決策紀錄分開放
[data-strategy.md](data-strategy.md) 放**還在收斂中**的設計,每一節標
[實測]/[提議]/[待驗]/[待決];decisions.md 只放**已定案**的。

理由:2026-08-19 那次討論產出了大量有數字支撐但還沒定案的提議(三層架構、
conductance 邊界、每日瀏覽量不進 Neon)。全部寫進 decisions.md 會讓「已定案」
這件事失去意義,新 session 會把提議當成規格照做;全部只留在對話裡則會遺失。

**規則:提議定案時才搬進 decisions.md,並註明「取代 #N」。**

### 23. Embedding 只掛在節點上,永遠不決定圖結構
**圖的邊是否存在、邊的權重,一律只由維基百科的真實超連結決定**(`graph_build.py` 建邊 +
`weighting.py` 的拓樸相似度)。Embedding 的用途限縮成兩項:

1. **語意搜尋**(`nodes_passage_vector`,查詢向量由 Worker 端即時產生)
2. **掛在節點上的資料**(節點特徵),例如 L1/L2 推導層的主題質心相似度

**明確排除**:用 cosine 相似度建邊、用 cosine 相似度加權既有的邊、以及 GraphRAG 那條
「用 LLM 從文本抽關係建圖」的路線。

理由,依重要性:

- **舊版試過,效果不好。** 查證 `docs/legacy/` 與本機原始檔,確認舊專案沒有留下任何 embedding
  加權的程式碼(只剩 `WikiNetwork.__init__` 裡兩個從未被賦值的屬性),使用者回憶是實驗後刪掉的。
- **真實連結是這個專案的核心資產,不該被稀釋。** 維基百科的超連結是幾十萬編輯者人工標註的關係:
  確定性、單一型別、實體解析由 redirect 表保證(我們的 `resolve_titles` 就是查表版的 entity
  resolution)。GraphRAG 整個領域最貴也最不可靠的一步 —— LLM 抽取實體與關係,失敗模式包括
  coreference 碎裂成多個節點、謂詞命名不穩定、跨 chunk 漏抽、且沒有 ground truth 可驗證 ——
  正是在花錢模擬我們免費就有的東西。用 cosine 覆寫邊等於把這個優勢丟掉。
- **單一關係型別是拓樸加權能成立的前提。** `|N(u)∩N(v)|/|N(v)|` 預設所有邊可比較;
  混入語意邊之後「共同鄰居」的意義就模糊了,Infomap 同理。

⚠️ 這條不排除未來拿 embedding 當 GNN / feature propagation 的節點特徵輸入,但那是 v1 範圍外的
研究方向,不在作品集的承諾清單裡。

### 24. 產品重心是瀏覽量資料的活化,語意搜尋降為加分項
**取代決策 #20 裡「瀏覽量不是這個作品集的核心賣點」那句判斷。**

使用者原話:「我應該專注在做好的產品,也就是 pageviews 資料的應用活化就好,不要想太多
embedding 方向的應用,那個只是搜尋的錦上添花而已,沒有也完全不重要。」

功能優先序因此是:

1. **連結網絡 + 社群偵測** —— 圖本身,專案的骨架
2. **瀏覽量的活化** —— 異常偵測、趨勢、社群層級的流量變化,產品價值在這裡
3. 語意搜尋 —— 有很好,沒有不影響作品的完整性

⚠️ 這條會回頭影響幾個在「瀏覽量不重要」前提下做的決定,見待決事項 N/O/P。

### 25. Phase 3(embedding)延後到 Phase 4-6 之後
**取代 roadmap.md 的階段順序。** Embedding 在決策 23/24 之後只支撐「語意搜尋」這個加分項,
卻同時是兩個前置阻塞(要開 Cloudflare 帳號、要先跑實驗 4 量 Neuron 消耗)。
把一個非核心功能排在核心路徑前面沒有道理。

新順序:**Phase 4(寫入 Neon)→ Phase 5/6(後端 + 前端,含瀏覽量活化)→ Phase 3(embedding)**。
`nodes_passage_vector` 表照建、先留空;Phase 5 的搜尋端點先不註冊路由,等 Phase 3 補上。

⚠️ **一個順序陷阱**:embedding 的模型與維度(決策 7、待決 B)、以及 `vector` vs `halfvec`
(實驗 3)仍然必須在 **Phase 4 建表前**決定,不能跟著 Phase 3 一起延後 —— 否則建好的表
之後要重建、向量全部重算。

### 26. 瀏覽量不抽樣,所有收錄節點都抓
**取代 data-strategy.md 5.4 的「每主題只抓瀏覽量前 10% 節點」提議。**

5.4 的論證是「前 10% 的節點涵蓋 68% 實際流量」。這個數字沒錯,但**只對「主題總流量趨勢」
成立,對異常偵測不成立** —— 而異常偵測才是產品重心(決策 24)。

**按瀏覽量抽樣,跟異常偵測想找的東西方向相反:** 前 10% 是穩定的熱門條目(物理學、數學這類),
瀏覽量本來就平穩、z-score 難以觸發;真正有價值的異常是「平常沒人看的冷門條目突然爆紅」,
而那些全部落在被砍掉的 90% 裡。

成本不是障礙:實測併發 6 抓滿 13,085 個條目約 45 分鐘,GitHub Actions 在公開 repo 分鐘數
免費無上限。儲存也不是 —— 日資料留在 pipeline 端 SQLite(待決 I),進 Neon 的只有半月彙總
(10,000 節點 × 25 期 ≈ 15 MB)與異常表(3.9% ≈ 9 MB)。

⚠️ 5.4 那個「主題趨勢基於前 10% 條目、涵蓋 68% 流量」的**頁面標註仍然可以保留** —— 
只是它從「我們只抓了這些」變成「我們用這些代表趨勢」,是呈現上的選擇而不是資料的限制。

### 27. 完全不做每日更新,只保留每週 GitHub Actions
**取代決策 #6 的「輕量每日 Cloudflare Cron Trigger」。** 每日更新這件事整個刪掉 ——
不是搬到別的地方,是不做。`apps/api/src/scheduled.ts` 與 `wrangler.toml` 的 cron schedule
都不需要建立。

兩個理由,一個工程一個產品:

**工程面:每日更新的單位成本是每週的 7 倍,買到的是同一份資料。**
Wikimedia pageviews API 的計價單位是「條目」不是「資料點」(實測見下方「待決 P 的依據」),
一次請求可以拿任意長度的日期區間。所以每週跑一次,10,000 個請求換到 70,000 個新資料點;
每天跑,同樣 10,000 個請求只換到 10,000 個。多出來的只有「早 0-6 天知道」。

**產品面:瀏覽量的「即時性」在 2026 年不值那個工程複雜度。**
使用者的判斷:「這個年代瀏覽 Wikipedia 的人也很少了,大家問知識都傾向直接問 AI。」
這件事有官方數字支撐 —— Wikimedia Foundation 2025-10 報告人類瀏覽量年減約 **8%**
(2025 年 3-8 月 vs 2024 同期,且是在修正 bot 偵測演算法之後);後續分析指出
2025-03 到 2026-03 的年減達 **−10.6%**,與 LLM 進入主流的時間吻合。

⚠️ **這條的產品面理由與決策 24 有張力,見待決 Q 的「⚠️ 未解的矛盾」一節。**
決策 27 本身(不做每日更新)不受該矛盾影響 —— 工程面的理由單獨就足夠成立。

### 28. 瀏覽量做成**歷史資料產品**,不是即時儀表板
使用者的定調:「我們可以做成對 2026 年以前的資料應用,活化之前的資料。」

**這一條收掉了 #24 與 #27 之間的矛盾**(原記在待決 Q 底下):
沒有意義的是**即時性**(「本週什麼條目很紅」—— 在流量萎縮的年代確實越來越沒意思),
不是資料本身。**十一年的歷史紀錄才是產品。**

#### 讓這件事成立的關鍵實測 [2026-08-19]

per-article 端點**一次請求可以拿任意長度的日期區間**,所以歷史深度是免費的:

```
GET per-article/zh.wikipedia/all-access/user/图论/daily/20150701/20260801
→ HTTP 200, 572 KB, 4,050 個日資料點
```

**同樣一個請求,現在只拿 365 點,可以拿 4,050 點。** 請求數完全不變。

| | |
|---|---|
| 資料起點 | **2015-07-01**(再早回 404「沒有資料」;legacy pagecounts 端點是 per-project,對我們沒用) |
| 一次請求的深度 | 4,050 個日資料點 / 572 KB |
| 10,000 個節點的總成本 | 10,000 個請求 → **約 4,000 萬個資料點**,一次抓完 |
| 對照 | 目前的做法:同樣 10,000 個請求,只拿 365 萬點 |

順帶,衰退在單一條目上就看得到:`图论` 2015-07-01 是 **47** 次,2026-08-01 是 **20** 次。

#### 為什麼這個方向比即時儀表板好

- **它是一個真正的自然實驗。** 資料橫跨 AI 前(2015-2022)與 AI 後(2023-2026),
  同一批條目、同一個度量。「哪類知識的閱讀行為被 AI 取代得最快」是只有這種縱向資料
  答得出來的問題,而且**通過決策 24 的判準**(需要瀏覽量 × 主題/社群劃分的交叉)。
- **縱向資料不必等著累積。** data-strategy 5.3 原本的賣點是「跑越久越有價值」——
  但那要等好幾年才有東西可看。維基百科已經幫我們累積了十一年,**立刻就有結果**。
- **工程難度是下降的,不是上升。** 歷史資料不會回溯改變,所以是**一次性抓取**,
  不需要為它維護任何排程。

#### 儲存:走靜態檔,不進 Neon

半月彙總在十一年尺度下是 10,000 × 264 期 ≈ **264 萬列(約 160 MB)**,塞不進 Neon 免費額度。
但**歷史彙總永遠不會變**,剛好符合 data-strategy 4.4 已經定義的「靜態層」——
pipeline 產生 gzip 靜態檔丟 Cloudflare Pages,CDN 快取,**0 次 DB 查詢、0 Neon 成本**。
日資料仍然留在 pipeline 端 SQLite(約 4,000 萬列 ≈ 1 GB,不進版控)。

#### ⚠️ 這條產生的新問題:每週排程還剩什麼工作?

**尚未決定,下個 session 要處理。** 瀏覽量變成一次性抓取之後,每週 GitHub Actions
(data-strategy 5.2)原本的 7 項工作裡,第 4 項(抓瀏覽量 → 彙總 → 異常表)消失了。
剩下的是「重爬連結圖偵測新增/消失的邊」與其下游 —— 但如果產品是歷史分析,
**圖要不要也固定成一個快照?**

連帶影響:候選功能 **6「新增條目熱潮」依賴持續爬取**,在固定快照的方向下會消失。
取捨要記下來:少了一個功能與「排程重算」這個展示點,換到的是大幅簡化的工程與立刻可用的
十一年縱向資料。

### 29. 完全取消排程重算,資料是一個固定快照
**取代決策 #6 的全部內容,以及 data-strategy 5.2 的每週 GitHub Actions。**
`.github/workflows/recompute.yml` 不需要建立;Phase 10 從 roadmap 移除。

決策 28 讓瀏覽量變成一次性抓取之後,每週排程只剩「重爬連結圖」這一項,
而產品既然是歷史分析,圖也應該是同一時點的快照。資料重跑改成**手動觸發**
(pipeline CLI 本來就能跑),想更新就自己跑一次。

#### 連帶消失的三個問題

data-strategy 5.5 列了週期性重算會製造的三個治理問題,固定快照之後**前兩個直接不存在**:

| 原問題 | 固定快照之後 |
|---|---|
| 社群編號跨週漂移(前端配色、分享連結、書籤全失效) | **消失。** 只跑一次就沒有「跨週對應」這回事。決策 #16 的固定亂數種子仍然保留,但降級成「同次重跑可重現」而已 |
| Embedding 不能每週全跑,需要 content hash 比對 | **消失。** 只算一次 |
| 靜態檔與 Neon 必須同版 | **仍然存在**,但從「每週要處理的流程問題」變成「部署時做對一次」 |

#### 誠實記下失去了什麼

data-strategy 5.3 原本主張「每週排程不是維護,是資料生產」,並把「新增條目熱潮」
當成獨有賣點。這個論點隨排程一起消失。

**但它被更好的東西取代了**:決策 28 的十一年瀏覽量、以及決策 30 的條目誕生時間
(可回溯到 2001 年)。**縱向深度從「跑了幾週」變成「維基百科累積的二十五年」**,
而且立刻可用,不必等。

### 30. 條目的「誕生時間」用首次修訂時間,不用最早的瀏覽量資料點
使用者提議用「最早有 pageviews 資料的日期」當條目誕生點,好處是零額外請求。
**這個做法會失效,原因是資料邊界:**

```
pageviews API 的資料起點 = 2015-07-01(決策 28 實測)
图论 的實際首次修訂    = 2003-09-17(本次實測)
```

**繁中維基的核心學術條目絕大多數建立於 2003-2014**,它們的「最早 pageviews 日期」
會全部擠在 2015-07-01 這條邊界上 —— 也就是說,**在最需要這個特徵的那批條目上,
它退化成一個常數**。這是典型的左設限(left-censoring),不是可以忽略的誤差。

#### 改用首次修訂時間,並順手補存 page_id

```
GET /w/api.php?action=query&prop=revisions&titles=图论
    &rvdir=newer&rvlimit=1&rvprop=timestamp&formatversion=2
→ {"pageid":4622, "title":"图论", "revisions":[{"timestamp":"2003-09-17T11:45:43Z"}]}
```

⚠️ **這個端點不能批次**:實測帶兩個 titles 會回 `invalidparammix` ——
`rvdir=newer` / `rvlimit` 只能用在單一頁面。所以是 **1 個請求 / 條目**。

成本可以接受:10,000 個請求、併發 6 約 45 分鐘,而且因為決策 29 取消了排程,
這是**真正的一次性成本**。換到的是回溯到 2001 年的真實日期,
讓「主題隨時間的條目成長」變成二十五年的故事,而不是十一年的截斷版。

#### 順帶:`page_id` 應該存起來,目前沒有存

實測每個查詢回應本來就附帶 `pageid`(`图论` = 4622),**目前 pipeline 完全沒有存它**
(`wiki_pipeline/` 裡搜不到 `pageid`)。兩個理由值得補:

1. **它是穩定識別碼。** 目前所有東西都以 title 為 key,條目改名就會斷;`page_id` 不會變。
2. **它是免費的誕生順序代理。** `page_id` 大致單調遞增,`图论` = 4622 一看就是早期條目。
   即使不做決策 30 的首次修訂抓取,光靠它就能排出建立順序。

⚠️ 這需要改 `state.py` 的 schema 與 `wiki_api.py` 的解析,是 Phase 1 的小幅回頭修改。

- **(a) 換提問方式,不換資料 —— 傾向這個。** 把瀏覽量的主題從「什麼條目最近很紅」
  (nowcasting,在流量萎縮的年代確實越來越沒意思)改成**「知識消費的模式正在怎麼改變」**。
  衰退本身就是題目:**哪些主題撐得住、哪些崩得快?** 基礎數學條目 vs 時事條目的衰退曲線
  是不是不一樣?這需要瀏覽量 × 主題/社群劃分的交叉,剛好通過決策 24 自己訂的判準,
  而且**零額外工程** —— 同一批資料、同一條管線,只是換一個問法。
  使用者的觀察本身就是這個洞察,只是他當時是把它當成「不用太在意」的理由講出來的。
- **(b) 弱化決策 24。** 瀏覽量退回成一般功能,產品核心回到圖與社群偵測本身。
- **(c) 決策 24 照舊。** 認定「意義不大」只針對**即時性**,不針對資料本身。

⚠️ (a) 需要一件事先確認:**繁中維基是否也有同樣的衰退趨勢**,還是那 8% / −10.6% 主要來自
英文維基。這是一個 pipeline 端就能跑的小實驗(拿現有 160 萬筆日資料按主題分組看趨勢),
不需要任何雲端帳號。**如果繁中維基沒有明顯衰退,(a) 的前提就不成立。**

### 待決 P 的依據:瀏覽量 API 的經濟學 [實測 2026-08-19]

**核心事實:這個 API 的計價單位是「條目」,不是「資料點」。** 我們要的是
「很多條目 × 新的一天」,而 API 是為「少數條目 × 很多天」設計的 —— 剛好是轉置關係。

實測(都對 zh.wikipedia 打真的 API):

| 端點 | 一次請求給什麼 | 實測結果 |
|---|---|---|
| `per-article/.../daily/{start}/{end}` | **一篇**條目,任意長度的日期區間 | 單篇正常(`图论` 2026-07-14 = 29 views);**用 `\|` 串兩個標題會 404**,它把整串當成一個不存在的標題 —— **沒有批次語法** |
| `top/{project}/{access}/{y}/{m}/{d}` | **一天**內瀏覽量前 1000 名 | 一次回 **999 筆 / 54 KB**;但第 999 名就有 **604 views**,而 `图论` 只有 29 —— **我們的專業條目永遠進不了榜,這個端點對本專案沒用** |
| dump `pageview_complete/{y}/{y}-{m}/pageviews-{YYYYMMDD}-user.bz2` | **一天**內**所有專案所有條目**(含逐時) | **697 MB / 天**(2026-07-15 實測)。形狀正是我們要的轉置,但 98% 是其他語言的專案 |

**因此每日 vs 每週的差別是每請求效益,不是總量:**

```
每週更新:10,000 requests → 70,000 個新資料點   (每請求 7 點)
每日更新:10,000 requests → 10,000 個新資料點   (每請求 1 點)
```

**每日更新的成本效益正好是每週的 1/7,而換到的只是「早 0-6 天知道」。**
不是跑不動(45 分鐘 / 次,Actions 免費無上限),是**單位成本高 7 倍去買同一份資料**。
對一個作品集網站,這個交換划不來 —— 所以建議 (a) 每週 + 首頁標註資料時間戳。

⚠️ **逃生門記在這裡,免得以後重新推導**:如果哪天真的需要「每天、全條目、零遺漏」,
正解是下載每日 dump 檔串流過濾 `zh.wikipedia` 的列,而不是打 10,000 次 API。
代價是每天 697 MB 的下載與過濾工程。
