## 1. 核心發現:目前這張圖的「封閉度」只有 2.4% [實測]

### 什麼是封閉度

爬蟲的知識是不對稱的:拜訪一個條目時,只記得下**那個條目往外指的連結**。被指到的條目會進節點清單,但它自己指向誰,要等我們也去拜訪它才知道。

一組節點是**封閉**的 = 這組裡每一個節點都被展開過(問過外連),所以組內的邊全都知道,沒有漏。

### 實測數字

```
爬取:3 個種子 → 展開 → 312 個 depth-1 條目 → 展開 → 13,085 個 depth-2 條目 → 停

13,085 個節點中,只有 314 個被展開過        → 封閉度 2.4%
其餘 12,771 個只知道「誰指向它」,不知道「它指向誰」
```

具體證據 —— 資料庫裡出度為 0 的節點,在維基百科上其實是大樞紐:

| 條目 | 我們資料庫裡的出度 | 維基百科實際外連數 |
|---|---|---|
| 物理學 | 0 | **387** |
| 量子力學 | 0 | **370** |
| 向量空間 | 0 | **102** |

不是它們沒有連結,是我們沒去問。

### 為什麼這件事嚴重:它汙染了分析結果

18 個有效社群的特殊節點落點:

```
hub        18 個全部落在那 314 個已展開節點裡
center     18 個全部落在那 314 個已展開節點裡
bridge     18 個全部落在那 314 個已展開節點裡
authority  17/18 落在未展開的葉節點裡
```

`hub` 的定義是「指向很多重要節點的節點」。只有 314 個節點有出邊,所以 hub 必然是它們之一。**這個指標實際上在測「我們有沒有去問過它」,而不是在測維基百科的結構。** 這是會在面試裡被問倒的那種問題。

### 密度差 10 倍

把 12,771 個未展開節點全部丟掉,只留那 314 個(它們之間是完整的):

```
整張圖(13,085 節點)   平均出度  3.6
封閉子圖(314 節點)    平均出度 37.6
```

**節點數不是主要的品質槓桿,封閉度才是。** 500 個全問過的節點,比 13,000 個只問過 2.4% 的節點有價值得多,而且爬取成本更低(500 個請求 vs 13,000 個請求)。

重現:`python experiments/closure_check.py`(加 `--live` 會打真的 API 對照出度)

## 2. 架構轉向:多個精緻小圖 + 推導出來的大圖 [提議]

### 使用者提出的產品判斷

> 「我有很多種主題,每個主題的 source 不一樣,但展出的 node 彼此相對 dense,而且資料也可以抓全 —— 做精緻的小圖,這是使用者會覺得實用的內容。然而也需要有大圖,呈現主題跟主題之間的關係,以及主題之間的趨勢。」

這個判斷同時解決了封閉度問題:**主題範圍小,所以可以全部展開。**

### 三層,不是兩層 [提議]

| 層 | 內容 | 節點數(估) | payload(gzip 估) | 資料從哪來 |
|---|---|---|---|---|
| **L1 主題地圖** | 主題與主題的關係 | ~20 | ~3 KB | 推導 |
| **L2 子社群地圖** | 各主題內的子社群,跨主題可見 | ~140 | ~15 KB | 推導 |
| **L3 主題內部圖** | 單一主題的完整結構 | 300–800 | ~95 KB | 爬取 |

L1 只有 20 個節點,視覺上是張圖表而不是張圖 —— **L2 才是「大圖」該有的樣子**,而且它完全免費,還剛好用上已經移植好的兩層社群關係 meta-graph 程式碼(`communities.py::build_community_relation`)。

### 關鍵推論:大圖不需要抽樣,它是小圖的副產品 [實測]

拿那 314 個已封閉節點模擬「一個主題」:

```
封閉圖 314 節點 / 11,798 邊 → Infomap 分成 11 群
群大小: [178, 48, 32, 17, 12, 9, 5, 5, 4, 2, 2]

群內邊 10,982 (93%) / 跨群邊 816 (7%)
≥10 節點的群:5 個 → 10 種可能配對,實際有邊的 9 種
最強的跨群連結權重:212 / 80 / 62 / 55 / 51 / 50 / 46 / 43
```

分群語意乾淨:

| 群 | 內容 |
|---|---|
| 群3(48) | 樹(圖論)/ 四色定理 / 哈密頓圖 / 平面圖 / 完全圖 |
| 群9(32) | 網路科學 / 社會交換論 / 六度分隔 / 病毒營銷 / 人際關係 |
| 群5(17) | 小世界網路 / 複雜網路 / 隨機圖 / ER隨機圖 / 埃爾德什 |

**跨主題的邊佔 7%,權重有層次(212 到 43),9/10 配對都有連結。** 而這些邊目前正在被丟掉 —— 爬蟲抓到指向集合外的連結後直接捨棄。它們是零成本的,只要不丟就有。

⚠️ **風險 [待驗]**:上面 11 群裡有一個 178 節點的巨群(佔 57%),內容是「數學 / 電腦科學」泛稱條目。如果每個主題的 Infomap 都吐出一個巨群加幾個小群,L2 就撐不起 140 個節點。我判斷這是因為現在的種子(圖論/網絡科學/複雜網絡)本身太寬,主題化之後種子就是那個粒度了 —— 但這要真的跑過才知道。

重現:`python experiments/closed_subgraph_communities.py`

### L1/L2 的邊有四種,三種免費 [提議]

| 邊的類型 | 意義 | 成本 |
|---|---|---|
| **共享條目數** | 兩個主題重疊多少條目 | 免費,對使用者最直覺 |
| **跨主題連結數** | 結構耦合(實測佔 7%) | 免費,只要別丟 |
| **語意中心相似度** | 主題 embedding 質心的 cosine | 免費,向量本來就要算 |
| **讀者實際流動** | clickstream:讀者真的從 A 走到 B | 需處理 dump 檔(見第 6 節) |

**四種邊互相不一致的地方就是產品價值**:「這兩個主題結構上緊密相連,但讀者幾乎不在它們之間移動」是只有做過這個分析的人才講得出來的話。前端讓使用者切換邊的類型、看主題地圖重排,這個互動同時是好看的和有分析意義的。

## 3. 主題邊界怎麼定:節點預算不該是固定數字

使用者的質疑:「每個主題 500 封閉節點是不是有點太暴力?有些主題節點就是特別多但足夠 dense。」

**這個質疑是對的。** 第 2 節實測的自然群大小是 `[178, 48, 32, 17, 12, 9, 5, 5, 4, 2, 2]` —— 本來就不均勻,硬套 500 是錯的。以下是三個候選指標的實測結果。

### 3.1 候選指標一:入度 → 失敗 [實測]

「有多少個已收錄節點指向這個候選」。分布:

| 入度門檻 | 通過的候選數 | 佔比 |
|---|---|---|
| ≥ 1 | 12,771 | 100% |
| ≥ 2 | 5,744 | 45.0% |
| ≥ 3 | 3,746 | 29.3% |
| ≥ 5 | 2,165 | 17.0% |
| ≥ 8 | 942 | 7.4% |
| ≥ 20 | 165 | 1.3% |

質性檢查暴露問題:

```
入度 1     → 庫克-李文定理 / 子集和問題 / 揹包問題 / 完備(複雜度)   ← 都是核心主題!
入度 3-4   → 維基百科 / 國家科學基金會 / 心靈哲學                ← 完全不相關
入度 8-15  → 政治學 / 科際整合 / 勒內·笛卡兒                    ← 不相關
入度 20-99 → 物理學 / 數學家 / 經濟學                          ← 泛稱條目
```

**入度測的是「知名度」,不是「主題歸屬」。** 維基百科被所有東西連結;庫克-李文定理只被少數連結,但它是計算複雜性理論的核心定理。用入度當門檻會篩掉最專業的內容、留下最泛的條目 —— 方向是反的。**不要用。**

### 3.2 候選指標二:指回率 → 比較好,但對參照集過度敏感 [實測]

「候選節點的外連中,有多少比例指回主題內」。同一批候選,兩種參照集:

| 對候選池(13,085) | 對核心(314) | 指回池/核心/總外連 | 條目 |
|---|---|---|---|
| 100.0% | 62.5% | 8 / 5 / 8 | 匹配 (圖論) |
| 98.8% | 15.9% | 81 / 13 / 82 | 滲流理論 |
| 98.3% | 7.6% | 117 / 9 / 119 | 中心極限定理 |
| 90.5% | 4.8% | 19 / 1 / 21 | 庫克-李文定理 |
| 88.9% | 22.2% | 8 / 2 / 9 | 子集和問題 |
| 81.0% | 3.0% | 465 / 17 / 574 | 勒內·笛卡兒 |
| 72.6% | 5.4% | 281 / 21 / 387 | 物理學 |
| 71.7% | 4.0% | 215 / 12 / 300 | 政治學 |
| 69.2% | 23.1% | 9 / 3 / 13 | 揹包問題 |
| 65.2% | 2.3% | 512 / 18 / 785 | 經濟學 |
| 50.2% | 0.6% | 470 / 6 / 936 | 維基百科 |
| 44.2% | 7.7% | 23 / 4 / 52 | 國家科學基金會 |

- **對核心(參照集太小)**:專業條目變孤島。庫克-李文定理只拿 4.8%,輸給國家科學基金會 —— 因為它指向的 NP-完全、布林可滿足性問題還沒被收錄。
- **對候選池(參照集太大)**:什麼都算相關。維基百科 50.2%、勒內·笛卡兒 81%,都高於真正相關的揹包問題(69.2%)。

**絕對的指回率對參照集大小過度敏感,不能當單一門檻。** 但這張表裡藏著訊號:維基百科有 936 條外連,匹配(圖論)只有 8 條 —— **泛稱條目的特徵是「外連極多,但大部分指向主題外」**。

### 3.3 候選指標三:conductance(導電度)→ 方向正確 [實測]

`φ(S) = cut(S) / vol(S)`,用節點度數 normalize。把候選加進 S,看 φ 怎麼變:

```
目前核心 S(314 節點)φ = 0.60088

Δφ(負 = 讓主題更凝聚)        指回/外連   條目
  -0.00011   ✓ 收錄       5 /   8   匹配 (圖論)
  -0.00001   ✓ 收錄       3 /  13   揹包問題
  -0.00001   ✓ 收錄       2 /   9   子集和問題
  +0.00011   ✗ 拒絕       1 /  21   庫克-李文定理    ← 假陰性,但只差一點
  +0.00011   ✗ 拒絕      13 /  82   滲流理論        ← 假陰性,但只差一點
  +0.00022   ✗ 拒絕       4 /  52   國家科學基金會
  +0.00050   ✗ 拒絕       9 / 119   中心極限定理
  +0.00161   ✗ 拒絕      12 / 300   政治學
  +0.00189   ✗ 拒絕      21 / 387   物理學
  +0.00326   ✗ 拒絕      17 / 574   勒內·笛卡兒
  +0.00462   ✗ 拒絕      18 / 785   經濟學
  +0.00601   ✗ 拒絕       6 / 936   維基百科
```

兩個發現:

1. **泛稱條目被斬得非常乾淨。** 維基百科 +0.006 比邊界案例差 **50 倍**。排序完全符合直覺:越泛的條目排越後面。這是入度和指回率都做不到的事。
2. **剩下的假陰性只差 0.0001,而且原因可修。** 庫克-李文定理對 314 核心的指回是 1,對 13,085 池是 19 —— 它的鄰居還沒被收錄。**等鄰居進來,它自己會翻正。**

### 3.4 提議的算法 [提議]

不要對 Δφ 設閾值 —— 上表的絕對值只有 0.0001 量級,因為 S 已有 314 個節點,單一節點的影響被稀釋。**訊號在排序,不在數值大小。**

用標準做法(Andersen–Chung–Lang 的 local graph clustering / PageRank-Nibble):

```
1. 從主題種子跑 personalized PageRank,得到候選的排序
2. 按這個排序逐一加入,記錄每一步的 φ
3. 取 φ 的最小值那一刀 → 那個位置就是主題邊界
4. 重複 1-3 直到沒有新收錄(邊界案例會在第 2、3 輪翻正)
```

**主題大小變成輸出,不是輸入。** 而且這不是自己發明的啟發式,是有文獻的方法 —— 「主題邊界由 conductance 最小化決定」比「我設了 500」好講太多。

### 3.5 節點預算的新角色:保險絲,不是目標 [提議]

「任何主題超過 1,500 節點就停下來讓人工看一眼」—— 因為那通常代表種子下太寬(就像目前那個 178 節點的巨群,種子是三個都很寬的詞)。

### 3.6 共享爬取池,而不是每個主題各爬一次 [提議]

測試一個候選要花 1 個請求,但**被拒絕的候選不是浪費**:它的連結資料告訴我們邊界在哪,而且它很可能是**別的主題**的成員。所以應該是**一個共享的爬取池 + 多個主題視圖**。加第 20 個主題時,大部分候選已經展開過,邊際成本很低。

### 3.7 邊界邊要用標題當 key,不能用 idx [提議]

被主題 A 拒絕的候選,**可能被主題 B 收錄** —— 到那時候這條原本的邊界邊就變成一條真正的跨主題邊。所以:

```sql
boundary_links(source_idx, target_title)   -- 用標題,不是 idx
```

主題 B 收錄了那個標題之後,回頭 resolve 就得到 A↔B 的跨主題邊。零額外爬取。這實作了使用者說的「保留那些最往外的邊(跨群的邊的候選)」。

## 4. 儲存策略 [提議]

### 4.1 前端每個功能實際要下載多少 [實測]

以目前 13,085 節點的資料量測(gzip 後):

| 功能 | payload |
|---|---|
| 社群關係圖(43 節點 / 85 邊) | **2.8 KB** |
| 單一社群子圖(最大 132 節點 / 781 邊) | **9.2 KB** |
| 18 個子圖全部(1,544 節點 / 3,267 邊) | ~38 KB |
| 全圖 13,085 節點 / 47,391 邊 | **475 KB**(節點 277 + 邊 197;未壓縮 2.2 MB) |
| 節點簡介 | 0.3–1.2 KB |
| 日瀏覽量 365 點 | 1.0 KB |
| 半月 25 點 | 0.1 KB |
| 搜尋結果 10 筆 | 0.4 KB |
| 標題索引 13,085 筆(前端即時篩選) | 131 KB |

除了全圖,每個功能都是 KB 等級。**成本不在傳輸,在儲存。**

### 4.2 原計畫的 Neon 用量會爆掉免費額度 [實測 + 估算]

| `nodes`(含簡介,平均 1,227 bytes/列) | 13,085 | 18 MB |

| `pageviews_half_month` | 327 K | 20 MB |
| `anomaly_pageviews`(z>1.96 佔 3.9%) | 186 K | 12 MB |
| 其他(社群日瀏覽量、子圖、特殊節點) | | 1.3 MB |
| **合計** | | **~450 MB** |

Neon 免費方案是 **0.5 GB**(⚠️ 憑記憶,請到 dashboard 確認),而且不含分支歷史與 WAL。照原計畫直接寫,Phase 4 當天就爆,`dev`/`main` 兩個 branch 都開不起來。

### 4.3 三個削減:450 MB → 110 MB [提議]

**(1) 每日瀏覽量完全不進 Neon(−280 MB)**

實測 Wikimedia pageviews API 的回應標頭:

```
access-control-allow-origin: *
cache-control: s-maxage=14400, max-age=14400
```

**它本來就開放瀏覽器直接打,而且給 4 小時快取。** 我們在複製一份公開 API 已經免費提供、還幫我們 CDN 快取好的資料,並為此付 280 MB。

改成 Worker 代打 + Cache API(代打而非瀏覽器直打,是為了帶合規的 User-Agent 並吃邊緣快取)。使用者點開一個節點才抓那一個節點的 365 天,1 KB。

**副作用:資料完整性問題直接消失。** 目前 13,085 個條目只有 4,645 個有瀏覽量(35%)。改成按需抓取後沒有「缺資料」這回事,而且抓到的是當天最新的,不是某次批次跑的快照。

異常偵測怎麼辦?z-score 需要全域資料,但那是 **pipeline 端的批次工作**(GitHub Actions 讀它自己的 SQLite),只有**異常的那 3.9%** 寫進 Neon。Phase 5 的「使用者拉時間區間即時重算」則是對瀏覽器已經抓到的那 365 點做運算,不需要 DB。

**(2) `vector(1024)` → `halfvec(1024)`(−60 MB)**

pgvector ≥ 0.7 的 `halfvec` 是 float16,每維 2 bytes:115 MB → 55 MB。
⚠️ 一般報告的 recall 損失在 1% 以內,但**不要憑印象採用** —— Phase 4 要拿同一組查詢對 float32 / float16 兩種索引跑比對,數字不能接受再換回來。也要確認 Neon 的 pgvector 版本 ≥ 0.7。

**(3) 靜態圖資料不進 DB 查詢路徑(架構層,不只省空間)**

全圖 / meta-graph / 子圖 / 標題索引**每週重算一次才變**,卻放在每個訪客的首屏路徑上。兩個具體問題:

- Neon 免費方案閒置 5 分鐘 auto-suspend,第一個訪客要等冷啟動
- Workers 免費方案每次調用 **10 ms CPU**,序列化 475 KB JSON 很可能超

pipeline 直接產生 gzip 靜態檔丟 Cloudflare Pages(免費、頻寬無上限、CDN 快取)。首屏 2.8 KB 從 CDN 來,0 次 DB 查詢、0 compute hours。

### 4.4 三層儲存 [提議]

| 層 | 內容 | 位置 | 大小 |
|---|---|---|---|
| **靜態(每週重生)** | 全圖、L1/L2 地圖、子圖、標題索引 | Pages 靜態資產,gzip | ~650 KB |
| **必須可查詢** | 簡介、embedding、異常表、半月/社群瀏覽量 | Neon | ~110 MB |
| **不存,按需抓** | 每日瀏覽量 | Wikimedia API ← Worker + Cache API | 0 |

Lazy load 的層次就是使用者的操作路徑:首屏 2.8 KB → 點主題 9–95 KB → 點節點(簡介 1 KB + 瀏覽量 1 KB)→ 想看全圖才載那 475 KB。

### 4.5 多主題設計下的成本 [估算]

每個封閉節點的邊際 Neon 成本:

| | |
|---|---|
| `nodes` 列(簡介 1,227 B + 索引) | 1.4 KB |
| `halfvec(1024)`(heap 2.1 + HNSW 2.1) | 4.2 KB |
| 邊(約 40 條/節點 × 80 B) | 3.2 KB |
| **合計** | **~9 KB / 節點** |

| | |
|---|---|
| 每主題 500 封閉節點 | ~4.4 MB |
| 20 主題(10,000 節點) | ~88 MB |
| L1/L2 邊、主題趨勢、縱向記錄、異常表 | ~7 MB |
| **合計** | **~95 MB(19% 免費額度)** |

跟「10,000 節點扁平圖」**完全相同的預算**,但封閉度從 **2.4% → 100%**。

免費額度的節點上限約 **3.5 萬**(0.5 GB ÷ 9 KB,再扣歷史與 dev branch 餘裕)。

### 4.6 一個可以刪掉的 hack [提議]

舊專案 `topology_view_edges` 那個「每個 source 取權重前 3 名、補到 1,000 條」的裁切(實測在現有圖上得到 941 條邊)—— 在多主題設計下**可以整個刪掉**,因為永遠不會一次渲染超過一個主題(500 節點 / 20,000 邊 = 95 KB gzip)。

⚠️ 但如果最後決定保留「全圖」視圖,裁切還是需要的:封閉圖 10,000 節點會有約 45 萬條邊 ≈ 1.9 MB gzip。

## 5. 定時任務(依新架構修訂)[提議]

### 5.1 每日 Cloudflare Cron Trigger:這個任務消失了

原計畫(decisions.md #6)它要做「抓最新瀏覽量寫進 `pageviews`、更新半月彙總」。**日瀏覽量不進 Neon 之後,它沒有工作了。**

硬要留,唯一有意義的候選是刷新首頁「最近異常」條(top ~40 節點,受 Worker 免費方案 50 個 subrequest 上限約束)。**提議 v1 不做** —— 留一個沒有實質工作的排程只是增加要維護的東西。

⚠️ 這件事**修訂了 decisions.md #6**,但還沒定案,所以 #6 目前還沒改。

### 5.2 每週 GitHub Actions:唯一真正的定期任務

| # | 工作 | 為什麼不能放 Workers |
|---|---|---|
| 1 | 增量爬取:重抓已收錄節點的外連,偵測新增/消失的邊 | 請求數遠超 subrequest 上限 |
| 2 | 重建圖 + 拓樸相似度邊權重 | — |
| 3 | 重跑 Infomap 社群偵測 | **Workers 是 V8 isolate,沒有 Python runtime,igraph/Infomap 跑不動** |
| 4 | 抓抽樣條目的日瀏覽量 → 半月彙總 + z-score 異常表 | 請求數超上限 |
| 5 | 只對簡介有變動的條目重跑 embedding | — |
| 6 | Upsert 進 Neon | — |
| 7 | 重生靜態圖檔 → 部署 Pages | — |

公開 repo 的 Actions 分鐘數免費無上限,所以這件事本身零成本。

### 5.3 每週排程不是維護,是資料生產

**「新增條目熱潮」這個功能完全免費,而且只有我們有。** 每週增量爬取會發現「本週『量子計算』主題新增了 12 個條目」。這是我們自己的縱向資料,維基百科的 API 不會給你「某個主題最近在長」這種資訊。

跑得越久,縱向資料越有價值,而這是任何人 clone 這個 repo 都複製不走的東西。這也是「為什麼要有定時任務」最好的答案 —— 比「保持資料新鮮」有說服力得多。

### 5.4 主題趨勢的抽樣率 [實測]

瀏覽量集中度(4,645 個節點、期間總量 5,676 萬):

| 抽樣 | 涵蓋總瀏覽量 |
|---|---|
| 前 1.1% 節點 | 31.0% |
| 前 4.3% 節點 | 51.7% |
| **前 10.8% 節點** | **67.8%** |
| 前 21.5% 節點 | 80.5% |

每個主題抽前 10% 代表趨勢,涵蓋約 68% 實際流量。20 主題 × 50 = **1,000 個請求/週**,而不是 10,000。

**這個數字要寫在頁面上**:「主題趨勢基於該主題瀏覽量前 10% 的條目,涵蓋 68% 實際流量」。有標註的抽樣是資料治理,沒標註的才是偷懶。

### 5.5 週期性重算會製造三個治理問題 [待驗 + 待決]

這是這個專案最值得展示的部分,而且都是這個架構真的會遇到的,不是為了展示硬加的:

1. **社群編號會漂移。** Infomap 每週重跑,「社群 7」這週是圖論、下週可能變成經濟學。前端的配色、分享連結、書籤全部失效。需要用成員重疊度把新社群對回舊 ID,並處理分裂/合併。(decisions.md #16 只解決了「同一次跑兩遍結果不同」,沒解決「不同週之間的對應」。)
2. **Embedding 不能每週全跑。** 需要對 extract 存 content hash,只重算變動的 —— 否則每週燒 10,000 次 Workers AI 呼叫產生一模一樣的向量。
3. **靜態檔與 Neon 必須同版。** 前端從 CDN 拿到的節點 idx,如果 Neon 還是上一版就會查不到。需要 dataset version 標記 + 明確的部署順序(先寫 Neon,再換靜態檔)。

## 7. 待跑的實驗 [待驗]

按優先序。**實驗 1 會驗證整個「精緻小圖」設計的前提,應該最先跑。**

### 實驗 1:主題邊界會落在哪裡(最高優先)

**做法**:展開入度 ≥ 5 的那 2,165 個候選(約 2,200 個請求,背景 15–20 分鐘),得到一張 ~2,500 節點的封閉圖。然後對「圖論」單一種子跑 PPR + conductance sweep。

**要看什麼**:
- 主題邊界自然落在幾個節點
- **φ 的曲線長什麼樣**
- 庫克-李文定理和滲流理論是不是真的在第 2 輪翻正

**什麼結果會推翻設計**:如果 φ 曲線**平坦、沒有明顯最小值**,就代表維基百科的連結結構在這個尺度上沒有清晰的主題邊界,「精緻小圖」的前提就要重新想(退路:用維基百科的分類樹或「基礎條目」當人工邊界,不靠算法)。

### 實驗 2:主題內的 Infomap 會不會又吐出巨群

**做法**:對實驗 1 得到的主題跑 Infomap,看群大小分布。

**什麼結果會推翻設計**:如果又出現佔 50%+ 的巨群,L2 子社群地圖就撐不起來,三層架構要退回兩層。

### 實驗 3:halfvec 的 recall 損失

**做法**:同一組查詢,對 `vector(1024)` 與 `halfvec(1024)` 兩種 HNSW 索引比對 top-10 重疊率。

**時機**:Phase 4,需要 Neon。

### 實驗 4:Workers AI 的 Neuron 消耗

**做法**:跑 10 筆 embedding,量實際 Neuron 消耗,反推 10,000 筆的成本與免費額度(每日 10,000 Neurons)夠不夠。

**時機**:Phase 3 開始前。pipeline 可續傳,真的撞到每日上限就分幾天跑。

### 實驗 5:社群偵測 vs 人工主題界線的一致性

**做法**:對所有主題的聯集跑一次 Infomap,用 NMI / adjusted Rand index 量「演算法找到的社群」與「人工策劃的主題」有多接近。

**為什麼值得做**:這是一個**量化的、可反駁的**評估結果(「NMI = 0.78」),而且它同時驗證了兩件事 —— 演算法合不合理,以及人工主題劃分合不合理。這是「科學項目」那一面最好的產出。
